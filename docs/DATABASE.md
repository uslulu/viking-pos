# База данных кассы

Касса хранит всё в своей базе на MS SQL Server: блюда и категории меню,
сотрудников, заказы и оплаты. Структура базы (имена таблиц и колонок)
досталась от первой версии программы, поэтому часть названий выглядит
странно. Например, сумма оплаты лежит в колонке `Qtty`. Ниже описано, как
программа работает с базой сейчас. Как перевести её на PostgreSQL или MySQL —
в [DB_MIGRATION.md](DB_MIGRATION.md).

## Подключение

| Что | Где задаётся | По умолчанию |
|---|---|---|
| Сервер | `config.ini` → `[database] server` | `localhost\SQLEXPRESS` |
| База | `config.ini` → `[database] database` | `cafel` |
| Драйвер | `db/connection.py` | ODBC Driver 17 for SQL Server (ставится в Windows отдельно) |
| Вход | `db/connection.py` | Windows-аутентификация (`Trusted_Connection`) |

- Пароля к базе нет. Касса входит под той учётной записью Windows, под которой
  запущена, и этой учётной записи нужен доступ к базе в SQL Server.
- Роли в кассе (кассир / администратор) ограничивают только экраны программы.
  В самой базе у всех одинаковые права — те, что есть у пользователя Windows.
- У каждого потока программы своё соединение. После минуты простоя оно
  проверяется запросом `SELECT 1` и при обрыве переподключается.
- **Создать пустую базу программа не умеет**: скрипта схемы в проекте нет.
  Новая точка сейчас получает копию существующей базы (резервная копия →
  восстановление).

## Таблицы

| Таблица | Что хранит | Где используется |
|---|---|---|
| `Operations` | Позиции заказов (продажа — `OperType = 2`) | касса, чеки, заказы, отчёты |
| `Payments` | Оплаты заказов | открытые и оплаченные заказы, отчёты |
| `Goods` | Блюда и товары, цены | меню кассы, экран «Товары» |
| `GoodsGroups` | Категории меню | меню кассы, экран «Товары» |
| `Users` | Сотрудники, пароли, роли | вход, экран «Сотрудники» |
| `Objects` | Точки / залы | касса берёт первый по имени |
| `Partners` | Контрагенты | контрагент по умолчанию для продаж |

В базе есть и другие таблицы из первой версии (`Store` — остатки, `UsersGroups`,
`OperationType` и т. д.), но касса их не читает и не пишет.

### Operations — позиции заказа

Одна позиция заказа — одна строка с `OperType = 2`. Все позиции одного заказа
связаны номером `Acct`. Отдельной таблицы «заказы» нет.

| Колонка | Что пишет касса |
|---|---|
| `OperType` | `2` — продажа |
| `Acct` | номер заказа (он же номер чека): `MAX(Acct) + 1` по всей таблице, выдаётся под блокировкой |
| `GoodID` | блюдо (`Goods.ID`) |
| `Qtty` | количество; «+»/«−» меняют его в той же строке |
| `PriceOut` | цена за единицу. **После оплаты со скидкой — цена уже со скидкой** |
| `Discount` | процент скидки (записывается при оплате) |
| `PriceIn` | себестоимость на момент добавления (`Goods.PriceIn`) |
| `Note` | `TABLE:<номер стола>` — к какому столу относится заказ |
| `OperatorID`, `UserID` | кто добавил позицию (`Users.ID`) |
| `PartnerID`, `ObjectID` | контрагент по умолчанию и первый объект |
| `Date`, `UserRealTime` | время добавления позиции |
| `Sign`, `VATIn`, `VATOut`, `CurrencyID`, `CurrencyRate` | постоянные `-1`, `0`, `0`, `1`, `1` — остались от исходной схемы |

### Payments — оплаты

При оплате на каждый способ пишется одна строка с тем же `Acct`.

| Колонка | Значение |
|---|---|
| `Acct`, `OperType` | номер заказа, `2` |
| `Qtty` | **сумма** оплаты этим способом |
| `Mode` | `0` — наличные, `1` — карта, `2` — перевод |
| `UserID`, `Date`, `UserRealTime` | кто и когда принял оплату |
| `PartnerID`, `ObjectID`, `Type`, `Sign` | контрагент, объект, постоянные `1` и `-1` |

В наличные записывается **выручка** (получено минус сдача). Полученная сумма
и сдача в базе не хранятся, только в напечатанном чеке.

### Users — сотрудники

- `Code` — логин, `Name` — имя в списке входа, `Deleted = 1` — уволен.
- `Password` — MD5 пароля (32 шестнадцатеричных символа). Если в поле что-то
  другое, оно сравнивается как открытый текст. Пустое поле — вход без пароля.
- `UserLevel`: `0` — кассир/официант (только касса), `1` — менеджер,
  `2` — администратор. Менеджер и администратор видят все разделы.

### Goods и GoodsGroups — меню

- В меню попадают блюда с `Deleted = 0`, категории — по `GroupID`.
- Цена на кнопке — `PriceOut1`. Если она `0`, берётся цена последней продажи.
  При нажатии касса ещё раз читает `PriceOut1`, чтобы новая цена сразу
  попадала в заказ.
- Удаление блюда — `Deleted = 1`. Удаление категории — блюда становятся
  «без категории», строка категории удаляется.

## Жизненный цикл заказа

```
 стол свободен ──(первая позиция)──► заказ открыт ──(оплата)──► заказ оплачен
                                      │    ▲
                                      │    └── +/−, удалить строку, добавить
                                      └──(отменить заказ)──► строки удалены
```

1. **Открытие.** Первая позиция на свободном столе создаёт новый `Acct`. Если
   этот стол уже открыт на другой кассе, позиция добавляется в его заказ.
2. **Открытый заказ** — позиции `OperType = 2`, для `Acct` которых **нет строк
   в `Payments`**. Статуса «открыт/оплачен» в базе нет, он вычисляется так.
3. **Изменения** (+/−, удаление, отмена) разрешены, только пока оплаты нет.
   Проверка и изменение идут в одной транзакции.
4. **Оплата** одной транзакцией:
   - проверяется, что заказ не оплачен и его сумма не изменилась;
   - при скидке в строки записываются цена со скидкой и процент;
   - добавляются строки `Payments`.
5. **Отмена** — позиции удаляются, от заказа в базе ничего не остаётся.

Две кассы не могут одновременно изменить и оплатить один заказ: обе сначала
блокируют оплаты этого `Acct` (`Payments WITH (UPDLOCK, HOLDLOCK)`), вторая ждёт
первую. Эта блокировка работает и тогда, когда строк оплаты ещё нет. Это
особенность SQL Server, и при переходе на другую СУБД её придётся заменить.

## Отчёты

- **Выручка, наличные / карта / перевод** — сумма `Payments.Qtty` за период по
  дате оплаты.
- **Заказов, по дням, топ блюд** — позиции оплаченных заказов за период по дате
  позиции.

Заказ, начатый до полуночи и оплаченный после, попадает в эти части отчёта в
разные дни.

## Полезные запросы (SQL Server Management Studio)

Перед ручными изменениями — резервная копия:
```sql
BACKUP DATABASE cafel TO DISK = 'C:\Backup\cafel.bak' WITH INIT;
```

Открытые заказы:
```sql
SELECT o.Acct, MAX(o.Note) AS Стол, SUM(o.Qtty * o.PriceOut) AS Сумма, MAX(o.Date) AS Последняя
FROM Operations o
WHERE o.OperType = 2
  AND NOT EXISTS (SELECT 1 FROM Payments p WHERE p.OperType = 2 AND p.Acct = o.Acct)
GROUP BY o.Acct ORDER BY MAX(o.Date) DESC;
```

Состав заказа и его оплаты:
```sql
DECLARE @acct INT = 123;
SELECT g.Name, o.Qtty, o.PriceOut, o.Discount, o.Note, o.Date
FROM Operations o JOIN Goods g ON g.ID = o.GoodID
WHERE o.OperType = 2 AND o.Acct = @acct;
SELECT Mode, Qtty AS Сумма, Date FROM Payments WHERE OperType = 2 AND Acct = @acct;
```

Выручка за сегодня по способам оплаты:
```sql
SELECT CASE Mode WHEN 0 THEN 'Наличные' WHEN 1 THEN 'Карта' WHEN 2 THEN 'Перевод' END AS Способ,
       SUM(Qtty) AS Сумма
FROM Payments
WHERE OperType = 2 AND CAST(Date AS DATE) = CAST(GETDATE() AS DATE)
GROUP BY Mode;
```

Оплаченные заказы, где сумма оплат не равна сумме позиций:
```sql
SELECT o.Acct, SUM(o.Qtty * o.PriceOut) AS Позиции,
       (SELECT SUM(p.Qtty) FROM Payments p WHERE p.OperType = 2 AND p.Acct = o.Acct) AS Оплаты
FROM Operations o
WHERE o.OperType = 2
  AND EXISTS (SELECT 1 FROM Payments p WHERE p.OperType = 2 AND p.Acct = o.Acct)
GROUP BY o.Acct
HAVING ABS(SUM(o.Qtty * o.PriceOut)
           - (SELECT SUM(p.Qtty) FROM Payments p WHERE p.OperType = 2 AND p.Acct = o.Acct)) > 0.01;
```

## Особенности и ограничения

- **Остатки не ведутся.** Касса не пишет в `Store`, продажи склад не списывают.
- **Номер заказа** — `MAX(Acct) + 1` по всем строкам `Operations`, без
  отдельного счётчика.
- **Статус заказа не хранится**: «открыт» значит «нет оплат». Удалённый
  (отменённый) заказ не оставляет следов.
- **Деньги** хранятся в тех типах, что достались от исходной схемы. Суммы и
  скидки касса считает с округлением до копеек на своей стороне.
- **Пароли** — MD5 без соли.
- В версиях до 1.0.1 при сдаче больше суммы заказа наличные могли не
  записаться. Такие оплаты в базе не исправлены, найти их можно последним
  запросом выше.
