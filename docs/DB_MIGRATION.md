# Переход с MS SQL Server на PostgreSQL / MySQL

Цель: чтобы новый терминал настраивался без установки SQL Server, ODBC-драйвера
и прав Windows-пользователя в базе, а действующие точки переехали без потери
данных и простоя в часы работы.

## Почему сейчас тяжело

Настройка терминала сегодня требует:
- установить SQL Server (Express) или иметь его в сети;
- поставить ODBC Driver 17 for SQL Server — он ставится в Windows отдельно, не
  через `pip`;
- выдать учётной записи Windows права в базе, потому что вход идёт через
  `Trusted_Connection`;
- перенести копию существующей базы: создать пустую базу программа не умеет.

## Что в коде завязано на SQL Server

| Что | Где | Замена |
|---|---|---|
| Драйвер `pyodbc` + ODBC Driver 17, `Trusted_Connection` | `db/connection.py` | драйвер СУБД из `pip` (psycopg / PyMySQL), логин и пароль в `config.ini` |
| Параметры `?` | все запросы | у psycopg и PyMySQL — `%s` (решается слоем доступа, см. ниже) |
| `WITH (UPDLOCK, HOLDLOCK)` — блокировка, в том числе ещё не существующих строк оплат | `db/operations.py`, 5 мест | `SELECT … FOR UPDATE` по строке заказа или `pg_advisory_xact_lock` |
| `MAX(Acct) + 1` под блокировкой — номер заказа | `db/operations.py` | последовательность (`SEQUENCE` / `IDENTITY` / `AUTO_INCREMENT`) |
| `SELECT TOP n` | `db/goods.py`, `db/operations.py`, `ui/reports.py` | `LIMIT n` (PostgreSQL понимает и стандартное `FETCH FIRST n ROWS ONLY`) |
| `ISNULL(x, 0)` | `db/goods.py`, `db/operations.py` | `COALESCE(x, 0)` — работает везде, включая SQL Server |
| Обращение к строке как `r.Qtty` (особенность pyodbc) | `close_table` | обращение по имени через общий слой |
| SQL прямо в экранах, 11 запросов | `ui/pos.py`, `ui/orders.py`, `ui/printer.py`, `ui/reports.py` | перенести в `db/` |
| Нет скрипта схемы | — | схема в коде + миграции |

`CAST(x AS DATE)`, `ROW_NUMBER() OVER (…)`, `NOT EXISTS`, `GROUP BY` переносятся
без изменений.

## Какую СУБД выбрать

**Рекомендую PostgreSQL.**
- Блокировки: `SELECT … FOR UPDATE` и `pg_advisory_xact_lock(номер_заказа)`
  прямо заменяют то, на чём держится защита от одновременной правки и оплаты
  заказа. В MySQL это делается неудобнее: `GET_LOCK` действует на всё
  соединение, а не на транзакцию.
- Транзакционные изменения схемы: если обновление структуры базы упало,
  оно откатывается целиком. В MySQL изменения схемы не откатываются, и
  неудачная миграция оставляет базу наполовину изменённой.
- Точные деньги в `numeric(12,2)`, строгие типы.
- Бесплатный, ставится на Windows и Linux одним установщиком. Драйвер
  `psycopg[binary]` ставится через `pip` целиком, без системных драйверов.

MySQL / MariaDB тоже подойдёт, если он уже где-то есть. План ниже от этого не
меняется, отличается только слой блокировок.

## Где будет стоять база

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Один сервер PostgreSQL на точку** (мини-ПК или одна из касс) | работает без интернета; новые терминалы — только программа + адрес сервера в `config.ini` | нужен бэкап этой машины |
| **Облако** (VPS / управляемый PostgreSQL) | все точки в одной базе, общие отчёты, ничего не ставить на месте | без интернета касса стоит — для кафе опасно |
| **SQLite на терминале** | ноль настройки, файл рядом с программой | только если на точке ровно одна касса |

Для кафе с несколькими кассами — сервер на точке плюс ночная выгрузка
`pg_dump` во внешнее хранилище. Если слой доступа сделать как ниже, SQLite
можно оставить для одиночных точек, демо и автотестов без отдельной работы.

## План

Каждый шаг выпускается обычным обновлением (`--test` → проверка → `--promote`)
и сам по себе ничего не ломает: до шага 4 кассы продолжают работать на
SQL Server.

### Шаг 1. Навести порядок на текущей базе
- Перенести 11 запросов из `ui/` в `db/`: весь SQL окажется в одной папке.
- Заменить `ISNULL` на `COALESCE`, обращаться к строкам только по имени колонки.
- Описать схему в коде: таблицы и колонки, которые реально использует касса.
- Автотесты слоя `db/` на SQLite: защита от регрессий при всех следующих шагах.

### Шаг 2. Слой доступа, не зависящий от СУБД
- Рекомендую **SQLAlchemy Core** (уже есть в `requirements.txt`, сейчас не
  используется). Это не ORM, а построитель SQL.
  - Одно описание таблиц — и `CREATE TABLE` для любой СУБД (пустую базу
    программа сможет создать сама).
  - Параметры, `LIMIT`/`TOP`, `FOR UPDATE`, пул соединений — под нужную СУБД
    автоматически.
  - Миграции схемы — **Alembic**.
- Подключение — одной строкой в `config.ini`:
  ```ini
  [database]
  url = postgresql+psycopg://pos:пароль@192.168.1.10/pos
  ; url = mssql+pyodbc://...   — пока точка не переехала
  ```
  Старые ключи `server` / `database` продолжают работать для SQL Server.
- Блокировка заказа выносится в одну функцию с реализацией под каждую СУБД.
- Результат: одна и та же версия программы работает и на SQL Server, и на
  PostgreSQL.

### Шаг 3. Перенос данных
- Скрипт `tools/migrate_db.py`:
  1. создаёт схему в PostgreSQL;
  2. копирует блюда, категории, сотрудников, заказы и оплаты;
  3. выставляет счётчик номеров заказов на `MAX(Acct) + 1`;
  4. сверяет число строк и выручку по дням в обеих базах.
- Сначала прогон на копии базы с терминала и сравнение отчётов в программе.

### Шаг 4. Переезд точки
1. После закрытия смены: все кассы закрыты, открытых заказов нет.
2. Резервная копия SQL Server.
3. `migrate_db.py` → сверка.
4. На каждой кассе в `config.ini` указать `url` новой базы.
5. Утром проверка: вход, стол, оплата, отчёт за вчера совпадает.

Откат: вернуть старые настройки в `config.ini`. База SQL Server остаётся
нетронутой. Заказы, принятые уже в новой базе, придётся перенести обратно, поэтому
откатываться лучше в тот же день.

### Шаг 5. Своя схема
Когда все точки на PostgreSQL, миграциями Alembic исправить то, что
досталось от первой версии:
- таблица `orders` с номером стола, статусом (открыт / оплачен / отменён),
  временем открытия и закрытия, официантом и скидкой — вместо `Note = 'TABLE:5'`
  и правила «нет оплат — значит открыт»;
- `order_items` и `payments` с понятными именами (`amount` вместо `Qtty` у
  оплаты), деньги в `numeric(12,2)`;
- отменённые заказы помечаются, а не удаляются — для учёта;
- пароли — bcrypt вместо MD5 (переход при следующем входе сотрудника);
- остатки, если понадобятся.

Шаг 5 можно делать постепенно: каждая миграция маленькая и откатывается.

## Что нужно от вас для старта

1. **Схема настоящей базы** с терминала: в SQL Server Management Studio — база →
   Tasks → Generate Scripts → только схема (без данных). По ней будут точные
   типы колонок, индексы и связи. Сейчас план составлен по коду программы.
2. **Сколько касс на точках** и есть ли на точке компьютер, который можно
   оставить сервером. От этого зависит, где будет PostgreSQL.
3. Нужны ли **общие отчёты по нескольким точкам**: это аргумент в пользу облака
   или репликации в него.
